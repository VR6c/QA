1. INTRODUCTION
--------------------------------------------------------------------------------

1.1 Purpose
This Software Requirements Specification (SRS) document details the functional,
non-functional, interface, and architectural requirements for the QA & Product
Engineering Control Center (v2.2). It serves as the single source of truth for
software engineers, quality assurance personnel, system administrators, and
product management stakeholders.

1.2 Scope of the System
The QA & Product Engineering Control Center (PECC) is an enterprise-grade SaaS
web application designed to streamline quality assurance workflows, task
lifecycle tracking, product engineering delivery, role-based access governance,
automated performance reporting, deadline scheduling, and executive performance
analytics.

Key capabilities include:
- A 6-swimlane drag-and-drop Kanban workflow board with optimistic updates.
- An interactive, sortable data table for high-density task management.
- An Interactive Calendar View supporting Day, Week, and Month scheduling modes
  with dynamic sliding animated tab controls, view content transitions, and drag-and-drop deadline planning.
- An Automated Weekly & Monthly IMP Performance Reporting Engine with draft previews,
  GCIN notes (Good, Challenge, Improvement, Next Action), report finalization, and
  immutable task locking.
- Real-time executive KPI dashboards with dynamic target evaluation (Good vs.
  Excellence thresholds).
- Role-Based Access Control (RBAC) with granular user permissions, custom role
  management, and strict user-level data isolation.
- An immutable audit trail system for governance and compliance.
- Global System Configuration Engine and Owner Governance Management.

1.3 Definitions, Acronyms, and Abbreviations
- PECC: Product Engineering Control Center
- SRS: Software Requirements Specification
- RBAC: Role-Based Access Control
- SPA: Single Page Application
- JWT: JSON Web Token
- IMP: Key Performance Indicator tracking system for quality assurance milestones
- ODM: Object Document Mapper (Mongoose for MongoDB)
- UAT: User Acceptance Testing
- GCIN: Good, Challenge, Improvement, Next Action reporting framework

2. OVERALL DESCRIPTION
--------------------------------------------------------------------------------

2.1 Product Architecture Overview
The application follows a modern decoupled Monorepo architecture:
- Frontend Layer: React 19 SPA powered by Vite, Tailwind CSS v4, Zustand state
  management, TanStack Query v5, custom animated segmented tab controls (`CustomTabs`) with
  fluid sliding pill background indicators (`cubic-bezier(0.16,1,0.3,1)`), and smooth view entrance transitions.
- Backend Layer: Node.js & Express.js REST API with modular controllers,
  middlewares (Auth, RBAC Guard, Rate Limiter, Tenant Handler), and services.
- Database Layer: MongoDB v7+ with Mongoose schemas supporting tenant-scoped
  and user-isolated data persistence across 8 core models.

+--------------------------------------------------------------------+
|                         React 19 SPA (Vite)                        |
|  (Kanban Board, Data Table, Calendar, Reports, KPI, Admin Suite)   |
+---------------------------------+----------------------------------+
                                  | REST API (JSON)
+---------------------------------v----------------------------------+
|                        Express.js API Backend                      |
|  (Auth Guard, RBAC Middleware, Rate Limiter, Audit Logger Engine)  |
+---------------------------------+----------------------------------+
                                  | Mongoose ODM
+---------------------------------v----------------------------------+
|                          MongoDB Database                          |
|  (Tasks, Users, Roles, Permissions, ActivityLogs, Settings,        |
|   Owners, Reports)                                                 |
+--------------------------------------------------------------------+

2.2 User Classes and Roles

1. Super Admin:
   Full root access across all system modules: Admin Panel, User Management,
   Role/Permission Configuration, System Settings, Owner Governance, Data Exporters,
   Audit Logs, and Task Unlocking.

2. Admin / QA Lead:
   Access to all task boards, metrics, team tasks across all owners, KPI trackers,
   weekly/monthly report previews and finalizations, custom KPI configuration, and CSV exports.

3. Tester / Employee:
   Restricted access to personal tasks (strict user-level data isolation),
   drag-and-drop status changes, personal profile management, calendar schedule,
   and individual KPI submissions.

2.3 Operating Environment
- Client Requirements: Modern Evergreen Web Browsers (Chrome 110+, Edge 110+,
  Firefox 115+, Safari 16+). Minimum resolution: 1280x720.
- Server Requirements: Node.js runtime v20+, MongoDB v7.0+.
- Deployment Platform: Vercel / Docker containerized environments with support
  for local MongoDB fallback.

3. SPECIFIC FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

3.1 Authentication & Profile Governance
- REQ-AUTH-1 (User Login): System shall support secure username/email login with
  password verification using BCrypt hashing (10 rounds).
- REQ-AUTH-2 (JWT Token Issuance): On valid credentials, system shall generate
  a signed JSON Web Token (JWT) containing user ID, role, and permissions.
- REQ-AUTH-3 (Session Hydration): Front-end store (authStore) shall validate
  existing tokens on boot (/api/auth/me) and populate user state.
- REQ-AUTH-4 (User Profile Governance): Users shall be able to view their profile,
  edit personal information (full name, username, email, phone number, department, position, bio),
  change passwords, and select/upload an avatar image.
- REQ-AUTH-5 (Last Login Tracking): System shall update `last_login_at` timestamp
  in User document upon successful authentication.

3.2 Task Management & Workflow Engine
- REQ-TASK-1 (Task Lifecycle Swimlanes): System shall categorize tasks across 6
  defined primary workflow swimlanes:
  1. Feedback & Issue (feedback)
  2. In Progress (progress)
  3. Testing / QA (testing)
  4. QA Success (success)
  5. Done / Deployed (done)
  6. Backlog / Pending (backlog)
  System also supports extended status tag `done_production`.
- REQ-TASK-2 (Task Drag-and-Drop): Users shall be able to drag cards between
  swimlanes using @dnd-kit with optimistic UI updates and instant API status
  synchronizations.
- REQ-TASK-3 (Environment Tagging): Tasks must be tagged with target push-to
  environment (Development, Production, TestFlight, UAT).
- REQ-TASK-4 (KPI Category Linking): Tasks can be assigned an IMP KPI category
  (quick_test, finding_product_error, conduct_testing, new_idea, research_template).
- REQ-TASK-5 (Owner Allocation): Tasks can be assigned to designated owners/team
  members with role tags and custom color themes.
- REQ-TASK-6 (Deadlines & Delay Reason): Tasks support explicit developer datelines
  (`datelineDeveloper`), testing datelines (`datelineTesting`), overall due dates
  (`due_date`), completion timestamps (`completed_at`), and delay explanations (`delay_reason`).
- REQ-TASK-7 (Task Locking Engine): Tasks claimed within a finalized report
  (`kpi_claimed_report_id`, `kpi_claimed_month`) are immutably locked against
  editing or deletion. Unlocking requires explicit authorization via `/api/reports/unlock-task/:taskId`.

3.3 Interactive Views & Analytics
- REQ-VIEW-1 (Kanban Board): High-level visual column layout with quick status
  transitions, search filtering, and task detail modals.
- REQ-VIEW-2 (Sortable Data Table): Compact grid view with column sorting (Date,
  Title, Status, Owner, Environment) and inline action toggles.
- REQ-VIEW-3 (Interactive Calendar View): Visual schedule planning view providing
  Day, Week, and Month presets, drag-and-drop date rescheduling, and timeline tracking.
- REQ-VIEW-4 (Animated Segmented Tab Controls & View Transitions): Dynamic UI tab switcher
  (`CustomTabs`) providing a liquid sliding white pill background indicator (`cubic-bezier(0.16,1,0.3,1)`),
  icon scaling, active state color morphing, and smooth entrance view content animations (`.animate-tab-content-switch`).
- REQ-VIEW-5 (Weekly & Monthly Performance Reporting Engine): Reporting module capable of:
  - Generating weekly/monthly metrics previews (`/api/reports/weekly/preview`, `/api/reports/monthly/preview`).
  - Editing GCIN notes (Good, Challenge, Improvement, Next Action).
  - Finalizing performance reports (`/api/reports/finalize`) which automatically claims and locks associated tasks.
  - Viewing past report history and performance tier ratings (Good vs. Excellence).
- REQ-VIEW-5 (Executive KPI Dashboard & Goal Tracker): Visual analytics center rendering:
  - Task Status Distribution (Donut Chart)
  - Environment Breakdown (Bar Chart)
  - Daily Volume Activity (Area Chart)
  - Column Capacity Load (Bar Chart)
  - IMP Performance Targets comparisons with custom threshold modal.

3.4 Data Filtering & Export System
- REQ-FILTER-1 (Multi-Criteria Filtering): System must support real-time composite
  filtering by text query (Title, Reason, Remark), Status, Push-To Environment,
  Owner / My Tasks, KPI Category, Date Range (with Quick Presets), and Month Tabs.
- REQ-FILTER-2 (CSV Exporter): Users can export filtered tasks into standard
  .csv format containing full task schema attributes (including completion date,
  datelines, delay reasons, and KPI categories).

3.5 Role-Based Access Control (RBAC) & Governance
- REQ-RBAC-1 (Granular Permission Checks): Endpoints must enforce RBAC middleware
  (`requirePermission('module.action')`).
- REQ-RBAC-2 (Permission Matrix): Fine-grained permission codes enforced across modules:
  - User Management: `user.view`, `user.create`, `user.edit`, `user.status`, `user.delete`, `user.reset_password`
  - Role Management: `role.view`, `role.create`, `role.edit`, `role.status`, `role.delete`, `role.permission`
  - System Settings: `setting.view`, `setting.edit`, `setting.toggle`
  - Activity Logs: `activity.view`
- REQ-RBAC-3 (Data Isolation): Non-admin users are strictly isolated to view and
  edit only tasks created by or assigned to themselves.
- REQ-RBAC-4 (Immutable Audit Logging): All administrative and state-changing
  actions (USER_CREATED, ROLE_PERMISSIONS_CHANGED, SETTING_DISABLED, REPORT_FINALIZED) are recorded
  in ActivityLog with user metadata, IP address, user agent, timestamp, and before/after diffs.

3.6 System Configuration & Owner Governance
- REQ-SETTING-1 (Global Configuration Engine): System configuration keys stored in MongoDB
  (Setting model) control global application behaviors, feature toggles, security
  parameters, and UI defaults across categories (General, User, Security, Notification, Feature).
- REQ-OWNER-1 (Owner & Team Member Management): Super Admins can manage team member profiles
  (Owner model) with avatar links, roles, default flags, and color themes (`blue`, `purple`,
  `emerald`, `amber`, `rose`, `indigo`, `cyan`, `teal`, `slate`).

4. NON-FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

4.1 Performance & Responsiveness
- NFR-PERF-1: Backend API endpoints shall respond in less than 150ms under normal
  operating load (100 concurrent requests).
- NFR-PERF-2: Frontend UI rendering shall maintain 60 FPS during drag-and-drop
  operations on Kanban board and Calendar.
- NFR-PERF-3: Client state query caching (staleTime: 30000ms) prevents unnecessary
  re-fetching while allowing instant background refetch on user interaction.

4.2 Security & Compliance
- NFR-SEC-1: Passwords must be hashed using BCrypt prior to database storage.
  Plain text passwords shall never be logged or stored.
- NFR-SEC-2: API endpoints enforce rate-limiting (e.g., 5 login attempts per window,
  100 API calls per minute) to prevent brute force or denial-of-service attacks.
- NFR-SEC-3: Cross-Origin Resource Sharing (CORS) is configured to allow requests
  only from trusted client origins.

4.3 Reliability & Availability
- NFR-REL-1: Automatic database connection fallback (Production Atlas -> Local
  MongoDB fallback) guarantees maximum uptime during development/staging setups.
- NFR-REL-2: Global error boundaries in React prevent full app crashes in the
  event of unexpected runtime UI exceptions.

6. VERIFICATION & ACCEPTANCE CRITERIA
--------------------------------------------------------------------------------

1. Task Operations & Locking: Successful creation, modification, status transition
   via drag-and-drop, and deletion of tasks. Tasks claimed in finalized reports must
   reject updates unless unlocked via `/api/reports/unlock-task/:taskId`.
2. Calendar & Scheduling: Verification that tasks render accurately across Day,
   Week, and Month calendar modes according to developer/testing datelines and due dates.
3. Reporting Engine: Verification that weekly and monthly report previews calculate
   metrics dynamically, save GCIN notes, and lock tasks upon finalization.
4. Security & RBAC: Verification that regular non-admin users cannot access
   administrative endpoints (`/api/admin/*`) or view tasks belonging to other users.
5. Immutable Audit Trail: Verification that any administrative role change, setting
   toggle, or report finalization creates an entry in the ActivityLog collection.
6. System Settings & Owners: Verification that setting toggles dynamically reflect
   system capabilities and team owner badges maintain assigned color themes.
